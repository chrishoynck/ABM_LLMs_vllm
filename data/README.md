# data/ — where every dataset comes from and what it is used for

Almost everything in this folder is **synthetic**: generated by this repo's own
pipelines, with Qwen3.5-27B served through vLLM unless stated otherwise (the
multi-model arm adds two more live generators, §4a). Only
three inputs are real-world data (first section below); a handful more are
small hand-made seed files. Everything else is derived from those by a script
in `src/` / `scripts/` named in the tables.

This file is the provenance map. Status/cleanup details (what is live vs
historical) live in the per-folder `NOTES.md` files, which each table links to.

```
 REAL DATA                 HAND-MADE SEEDS                GENERATED (synthetic)
 HELIUS PHQ-9 survey  ──►  (persona, PHQ-9) pairs   ──►  post corpora
 PersonaHub/Nemotron  ──►  + generation prompts          (test_post/, finetune/,
 Bathina CDS lexicon ───────────────┐                     sensitivity/, ...)
                                    │                          │
                                    ▼                          ▼
                            distortion metrics          assessors (BERT regressor,
                            in the simulation           optimized PHQ-9 prompt)
                                    │                          │
                                    └──────────► GABM simulation runs (networks_post/)
```

## 4a. Multi-model generator arm (2026-09) — the `<tag>` convention

The paper's convergence result was single-model, so the same fine-tune corpus is
now regenerated by two more **student** generators, Gemma-4-31B-it and
Mistral-Small-3.2-24B (a further one, Kimi-Linear, was run and dropped; note at
the end of this section). Everything they produce is namespaced by a short
**tag**, and nothing shares a path with the Qwen files:

| Tag | Generator (alias → HF id) | vLLM env | Student decoding (temp / top-p) |
|---|---|---|---|
| *(none)* | `qwen27` → `Qwen/Qwen3.5-27B` | `.venv_vllm` (0.17.1) | 0.7 / 0.9 |
| `gemma4` | `gemma4-31b` → `google/gemma-4-31B-it` | `.venv_vllm_g4` (0.19.1) | 1.0 / 0.975 |
| `mistral` | `mistral-small-24b` → `mistralai/Mistral-Small-3.2-24B-Instruct-2506` | `.venv_vllm_g4` (0.19.1) | 0.15 / 1.0 |

Decoding is the *only* deliberate difference: each model keeps its vendor's
recommended instruct defaults with the same relative adjustment Qwen got
(temperature unchanged, nucleus truncation halved). The table lives in
[src/utils/create_data/loaders.py](../src/utils/create_data/loaders.py)
(`STUDENT_DECODING`), not in the scripts. Mistral's `generation_config.json`
sets the temperature (0.15) but no top-p, so the halved-truncation rule leaves
it at 1.0. Non-Qwen weights are cached outside `$HOME` in
`/gpfs/work5/0/prjs1820/hf_cache` (`HF_HUB_CACHE`, set in the jobs). Mistral is
loaded in its own format (`params.json`, `consolidated.safetensors`, `tekken.json`;
`config_format` / `load_format` / `tokenizer_mode` = `"mistral"` in
`loaders.get_llm`, as the model card recommends), so the HF shards in its cache
folder are unused. Its rendered chat template does not re-encode to the tekken
control tokens, so its prompts go to vLLM as token ids
(`test_phq9_llms._prepare_prompts`); Qwen and Gemma keep the text path. The
vendor `SYSTEM_PROMPT.txt` is not used: the tweet instruction is the system
prompt for every generator.

| Tree | Generated by | Used for |
|---|---|---|
| `finetune/<tag>/train_posts_<tag>.csv` | `run_finetune.sh` with `GEN_TAG=<tag> GEN_MODEL=<alias>`, iter_10 prompt, 3,000 personas | Fine-tuning that generator's own regressors |
| `finetune/<tag>/test_posts_<tag>.csv` | same driver, 300 personas | That generator's held-out set — scored by every estimator |
| `finetune/<tag>_minimal/test_posts_<tag>_minimal.csv` | `jobs/run_finetune_minimal.job` (`GEN_TAG=<tag>_minimal PROMPT=…/iter_0/prompt.txt`), same 3,000/300 personas | The minimal-prompt arm: panel (b)'s second regressor line and panel (c)'s minimal grading |
| `finetune/<tag>_textgrad/test_posts_<tag>_textgrad.csv` | `jobs/grade_posts_panelc.job` (`generate_test_data` with `optimized_tweets/Qwen3.5-27B_seed29/optimized_instruction_tweet.txt`), same 300 personas | Panel (c)'s TextGrad grading on the 300-block protocol, replacing the paper's 100×3 stored run |
| `finetune/personas_test_300.csv` | `build_personas test-extra --n 300 --keep 0` | The **shared** test personas: byte-identical to the 120+180 behind Qwen's `finetune/qwen/test_posts_qwen.csv`, so the arms are paired |
| `finetune/personas_calibration_1400.csv` | The (persona, phq9) pairs of Qwen's `finetune/qwen/calibration_posts_qwen.csv` in `agent_id` order (50 per level) | Lets another generator rewrite the calibration set with identical personas, scores, agent ids and hence neighbour draws (`--first-n`) |
| `finetune/gemma4/calibration_posts_gemma4.csv` | `jobs/calibration_gemma4.job`: `generate_test_data --first-n` over the file above, iter_10 prompt, default neighbour pool/seed | Gemma's paired, balanced counterpart of the Qwen calibration set; CDS-vs-PHQ-9 comparison across generators (not used for bias tables) |
| `*.csv.meta.json` | written by `generate_test_data` next to every `--output-csv` | Provenance sidecar: model id, resolved temp/top-p, engine + sampling + neighbour seeds, prompt path, vLLM version, timestamp |

**Held fixed across generators** (so the generator is the only moving part): the
prompt (`prompt_optimization_h/qwen27_baseline/iter_10/prompt.txt`), the
personas and their PHQ-9 targets, the engine seed (1234), the per-round sampling
seed (42+round), the neighbour seed (42) and neighbour count (5), 10 posts per
block, and — importantly — **the neighbour pool itself**: every model's agents
read "posts from others" sampled from the *Qwen* teacher corpus
(`DEFAULT_NEIGHBOR_ROOTS`, §4 row 1). Neighbour context is thus a controlled
input, not a per-model variable; the cost is that Gemma and Mistral prompts
contain Qwen-written context. Override with `generate_test_data --neighbor-source-dir`
if a future run should make each model read its own posts.

**Implementation style.** The driver
[scripts/assessment/run_finetune.sh](../scripts/assessment/run_finetune.sh) is
one script configured by environment variables, not a copy per model:
`GEN_TAG` / `GEN_MODEL` / `GEN_HF_ID` / `INIT_MODEL` / `PYTHON_GEN` /
`PYTHON_BERT` / `TEMP` / `TOP_P`. With `GEN_TAG` **unset it reproduces the
original Qwen run and its exact paths**; setting it switches every output to the
tagged tree above. Same idea for
`run_llm_assessor_on_heldout.sh <tag>`. Generation steps are chunked and
resumable (a re-run skips `agent_id`s already in the CSV), so a job that hits
the wall clock can simply be resubmitted.

**Dropped arm: Kimi-Linear-48B-A3B-Instruct** (`kimi-linear`, tag `kimi`; run
2026-09-03 to 09-11, removed from the results 2026-09-11). The arm ran end to
end with the pipeline above (3,000 + 300 blocks, decoding 0.6 / 0.975, vLLM
0.15.1 in `/gpfs/work5/0/prjs1820/venv_kimi015`; vLLM >= 0.16 corrupts the KDA
recurrent state across concurrent sequences, upstream vllm-project/vllm#41292),
but its posts do not follow the PHQ-9 conditioning, so a comparison under the
shared prompt is not meaningful. Observed on the valid 0.15.1 output:

- Tone is flat across PHQ-9 from the first post of a block (lexicon affect
  corr -0.12; Qwen -0.41, Gemma -0.56). Positive-word share does not rise at
  low scores (25% at 0-4 vs 21% at 20-27); only register markers move
  (lowercase openings 26% to 46%, profanity 4% to 8%, length). The score is
  read as one-sided severity: low = nothing to express.
- Within a block it anchors on its own posts: 16% verbatim repeats, 46%
  content-word overlap with earlier posts (Qwen 29%, Gemma 16%); 76% of posts
  open with "Just"; 2% reply to neighbours (Qwen 66 to 93%), yet the
  neighbour posts still drag its tone.
- Estimators regress to the mean: MentalBERT fine-tuned on its own posts has
  MAE 5.6 (Qwen 2.9, Gemma 2.4), bias +8 at minimal and -7 at severe.
- First-post prompt ablation (300 personas, one change per condition):
  repeating the score before the task or removing the style rules changed
  nothing; the band's mood words on the score line, or dropping the neighbour
  posts, each recovered about half of Qwen's effect; a short prompt stating
  the scale's meaning inline reached -0.43; the iter_0 seed prompt was as flat
  as iter_10. Reading: a 3B-active research checkpoint that does not map the
  score to a mood under the shared prompt; a fair run would need its own
  prompt, which breaks the design.
- Not reproducible across runs with fixed engine and sampling seeds (7%
  byte-identical posts; aggregates stable).

All outputs, evals, jobs, logs and the diagnostic scripts are archived at
`/gpfs/work5/0/prjs1820/archive_kimi_arm_2026-09-11/` (mirrors the repo
layout; `NOTES.md` inside). The alias and decoding row stay in `loaders.py`
for provenance.

## 5. Data splits — what trains, validates, and tests on what

Published as `tab:datasets` in the PNAS manuscript and as `tab:datasets` +
`tab:optimization_splits` in the CS thesis (Methods); this section maps those
tables to the actual files. A **block** = the 10 posts one persona writes at
one fixed PHQ-9 score.

### Base (teacher) set — assessor training and in-distribution eval

The base set (§4, `test_post/Qwen_Qwen3.5-27B/`) holds **12,000 blocks
(120,000 posts)** — verified on disk: 10k + 20k + 90k CSV rows across the
three seeds.

| Pipeline | Split | Where it lives |
|---|---|---|
| MentalBERT+MLP regressor | **Agent-level 80/10/10** → **9,638 / 1,237 / 1,125 blocks** (train/val/test). Split drawn at runtime by `prompt_optimizer.train_val_test_split` with the run's seed; seeds 34–38 each trained. | Regressors in `assessors/bert/teacher/models/`; the deployed seed-35 test split is materialized as `assessors/bert/teacher/test_blocks_seed35.csv` (11,250 rows = 1,125 blocks). |
| LLM-prompt assessor (TextGrad) | Does **not** consume the full split: iterative batched sampling from the base set (train batch n=7 blocks, val ≈40 blocks); only the final eval uses a full held-out test set. | Runs in `test_post/optimized_phq9/`. |

**Alignment caveat:** the two pipelines seed their splits independently, so
they have no shared native test set. For all in-distribution comparisons the
LLM assessor is **re-scored on the seed-35 BERT test blocks** (the 1,125 above),
so both are judged on identical data (`run_phq9_on_bert_testset.sh`).

### Human-optimized corpus — fine-tune and distribution-shift splits

Generated with the iter_10 prompt by `scripts/assessment/run_finetune.sh`
(persona-disjoint by construction, see §2 builders):

| Role | Data | Where it lives |
|---|---|---|
| Fine-tune training | 3,000 personas (`personas_finetune_phq9.csv`) → training posts | `finetune/qwen/train_posts_qwen.csv` |
| Shared test / shift set | **300 blocks** = 120 pre-existing + 180 newly generated for unseen personas (`finetune/personas_test_extra.csv`) | `finetune/qwen/test_posts_qwen.csv` (extra half also in `qwen/test_posts_extra_qwen.csv`; the 120 originate from `prompt_optimization_h/.../SA_prompt/`) |
| Bias calibration | Balanced blocks from fully unseen personas (`finetune/personas_unseen_pool.csv`) → per-level bias table | `finetune/qwen/calibration_posts_qwen.csv` |
| LLM-prompt assessor (TextGrad, human corpus) | Train/val = the same 3,000 training blocks (2,700 / 300, fixed val subset of 40, batches of 7 × 8 steps, minimal start prompt); test = the same 300 blocks | `test_post/optimized_phq9_human/` (`jobs/run_prompt_optimizer_phq9_human.job`) |

The same 300 blocks double as the **distribution-shift set**: every estimator
(fine-tuned/baseline regressor, optimized and minimal LLM prompt) is re-scored
on them, which is what makes the shift comparison paired
(`run_eval_comparison.sh`, paper row "Assessment, distribution shift").

### Multi-model arm — one held-out set per generator, three estimators each

Per tag, `run_finetune.sh` regenerates the *same* split roles with that
generator: 3,000 training blocks and 300 test blocks (the shared personas
above). Its 300 blocks are then scored by five estimators, which is what fills
the generator × estimator table:

| Estimator | Regressors / prompt | Output |
|---|---|---|
| MentalBERT+MLP, Qwen-trained baseline | `assessors/bert/teacher/models/` seeds 34–38 | `assessors/bert/teacher/eval/on_<arm>/` |
| MentalBERT+MLP, fine-tuned on **Qwen** posts (cross-generator transfer) | `assessors/bert/qwen27_optimized/models/` | `assessors/bert/qwen27_optimized/eval/on_<arm>/` |
| MentalBERT+MLP, fine-tuned on **this generator's** posts | `assessors/bert/<arm>/models/` | `assessors/bert/<arm>/eval/on_<arm>/` |
| LLM prompt, minimal | Qwen assessor, prompt seeds 23/24/25/32/33 | `optimized_phq9/Qwen3.5-27B_seed<s>/minimal_<tag>300/` |
| LLM prompt, TextGrad-optimized | same | `optimized_phq9/Qwen3.5-27B_seed<s>/eval_on_<tag>300/` |

The assessor is always **Qwen3.5-27B** — only the *writer* of the posts changes,
which is the comparison the paper's limitation asks for. Qwen's own row reuses
the existing `eval_baseline/`, `eval_finetuned/`, `minimal_human300/` and
`eval_on_human300/` directories, untouched.

### Sensitivity analyses — no train/test split, a paired design

Each SA setting generates 60 personas × 10 posts, with every non-varied input
(personas, neighbour posts, per-slot PHQ-9) held fixed across settings:
stochastic axes 4 settings × 3 replicates, PHQ-9 conditioning 5 bands × 3,
decoding 7 settings × 3. Personas come from the shared anchor set (§2), never
from training pools.

> Known 10× slip: the CS thesis Methods prose (and, formerly, this repo's
> README) describes the base set as "≈1,200 blocks / ≈12,000 posts"; the
> on-disk counts and the PNAS split figures (9,638+1,237+1,125 = 12,000
> blocks) show it is 12,000 blocks / 120,000 posts. Fix manuscript-side.

## Caveat that trips people up

The teacher/high-fidelity set (§4 row 1) was generated with the *early*
`prompts_post.json`, while everything downstream of the optimization study uses
the human-optimized prompt — the two post distributions differ, and the
assessment results mix them in documented ways. Full explanation:
[README.md → Known caveat](../README.md#known-caveat--assessment-and-generation-results-come-from-different-datasets).
